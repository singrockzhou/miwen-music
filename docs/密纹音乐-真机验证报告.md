示例曲走的是计时器引擎，**不产生真实音频**，所以专门加了「播放自检」：内置 4 秒扫频 WAV，从 rawfile 落到沙箱后走真实 `openReal` 链路。

日志证据：

```
PlayerCore: state -> prepared
PlayerCore: state -> playing
CONTINUOUS_TASK: StartBackgroundRunningSubmit background task mode: 2, continuousTaskId: 462
PlayerCore: background audio task started
MC: controllerCallback {"appName":"密纹音乐","playState":2,"validCommands":["play","pause","stop","playNext","playPrevious","seek"]}
MC: collectSong ... playTimeTotal: 3.994 s
PlayerCore: state -> completed
```

- `prepared → playing → completed`：AVPlayer 状态机完整走通
- `playTimeTotal: 3.994 s`：系统统计的真实播放时长，与 4 秒测试音吻合，**不是 UI 假进度**
- 播放页显示 `WAV · 22.1 kHz`，总时长 `-00:03` 由 `durationUpdate` 回填（Track.duration 传的是 0）
- 播控中心（下拉控制中心）能拿到曲名、艺人、进度，`play`/`pause`/`stop`/`next`/`prev`/`seek` 指令齐全

顺带修掉本轮暴露的一个真缺陷：

**进入播放页不主动拉快照**。`aboutToAppear` 只订阅 `onChange`，而"解码失败""暂停"这类静置状态不会再发通知，页面就会停在空快照上——错误横幅因此永远不出现。已在 `PlayerPage` / `MiniPlayer` / `Index` 三处补 `this.core.snapshot()` 首拉。

关于 2.5 秒的实际观感：错误文案在本机折成两行（`无法解码该文件（示例：APE/DSD 需要转成 FLAC 或 PCM）`），2.5s 够辨认"出错了 + 已跳过"，但读不完整段括注。想更从容有两条零风险路子：把文案缩成"无法解码该文件 · 已跳到下一首"（细节留在设置页说明），或依赖"连错 3 次停下"时横幅保持（目前已是这个行为）。

## 七、文件夹树与多根目录（第三轮，13:10–13:30）

本轮新增 Pro 1.1 的第二个功能。验证目标不是"能编译"，而是"三条最容易在真机崩掉的路径"：
老索引升级、重装后授权失效、多根并存与嵌套。

### 7.1 老索引升级（1.0 → 1.1）

1.0 建的索引没有 `root_path` / `folder` 两个字段。不处理的话，设置页显示 3 首、文件夹管理页显示 0 首
—— 同一份数据两处自相矛盾，用户第一反应是"这版把曲库搞坏了"。

启动时补一次归属，真机日志：

```
TrackStore:   adopted 3 orphan rows
EntryAbility: adopted 3/3 orphan tracks
```

管理页随即从「1 个目录 · 0 首」变成「1 个目录 · 3 首」，卡片显示「3 首 · 1 个文件夹」。
只在**恰好一个根**时执行：多根时无从判断哪首属于哪个目录，猜错比空着更糟。

### 7.2 重装后授权失效 → 重新授权救回

这是本轮最有价值的一条。`fileShare.persistPermission` 在重装后会失效：

```
LibraryService: probe /storage/Users/currentUser/Download failed code=13900001
```

界面如实显示「需重新授权」+ 左侧铜金竖线，管理面板里的文案也跟着变（「重新授权（当前打不开）」/「重装后需要」）。
重选同一个目录后：

```
LibraryService: picked file://docs/storage/Users/currentUser/Download
LibraryService: found 3 audio files under /storage/Users/currentUser/Download
```

`path` 不变、`uri` 变了，按 path 配回旧记录 —— **不重扫、不丢歌单、不联网**。
状态标签随即从「需重新授权」变「可读」。

### 7.3 本轮修掉的三个真缺陷

| 现象 | 根因 | 修法 |
|---|---|---|
| 重新授权后状态标签仍停在「需重新授权」，但日志里 probe 明明成功 | `ForEach` 的 key 只用 `root.path`，重新授权时 path 不变 → 判定"没变"→ 复用旧子组件，`@Prop` 收不到新值 | key 改 `path_alive_count`；根卡片同时从 `@Builder` 抽成 `@Component` |
| 同一首歌可能同时属于两个根 | 允许把某个已授权目录的**子目录**再加进来 | `RootService.add` 返回 `added/exists/nested/invalid` 四态，嵌套直接拒绝并说明 |
| 管理页显示「0 首」而设置页显示「3 首」 | 老索引 `root_path` 为空 | 启动时 `TrackStore.adoptOrphans` 补归属 |

顺带：`folderCount` 把"根下直接放的曲目"（`folder` 为空串）误算成一个文件夹，改成
`COUNT(DISTINCT CASE WHEN folder <> '' THEN folder END)`；`RootService.list()` 会清掉历史遗留的嵌套根。

### 7.5 仍未覆盖

- **多根目录下的真实交叉验证**：设备上只找到两个有音频的目录（`Download` 与其子目录 `com.freeplay.music.hm`），
  后者恰好是被父目录覆盖的嵌套场景，所以"两个互不相交的根各自扫描"只在逻辑层与 UI 层验证过，
  没有两个真实不同的音乐目录可测。
- **5000 首规模下的树性能**：`folderStats` 的 GROUP BY 在 3 首规模下无法体现耗时，
  按索引设计与分页策略预计无问题，但**没有实测数据**，不要在对外材料里写成"已验证"。
- **目录改名后的表现**：`folder` 存的是扫描时的相对路径，改目录名后旧记录会指向不存在的路径，
  直到重扫才更新。当前不会崩（播放时才报"文件已失效"），但也没有"检测到目录已改名"的提示。

   加 `nextFailIndex` 记住失败索引，`playAt` 时重置；同一索引只试一次。
2. **逐行歌词把元数据冲空**（已真机复核通过）：`pushLyricLine` 只推 `{assetId, singleLyricText}`，
   `setAVMetadata` 是整份覆盖而非字段合并，`title/artist/duration` 全部变空，`duration` 恰是系统算桌面歌词进度的基准。
   改为 `fullMeta(t)` 统一产完整元数据，逐行推送与清词都从这里取，再挂 `singleLyricText`。复核后高亮逐行跟随（11.3）。
3. **交叉淡入淡出其实是「硬切 + 淡入」**：`fadeTick` 一等到预加载就 `swapToNext()`，而 `swapToNext` 里立刻
   `quietRelease(oldP)`——旧曲在新曲起播的同一刻被销毁，日志显示 `crossfade start` 与 `seamless switch` 只差 **104ms**，
   与界面上写的「两曲交叠 3 秒」不符。改法：`swapToNext(keepOld = true)` 把旧实例挂到 `fadeOld`，`fadeTick` 里
   旧曲 1→0、新曲 0→1 同时走，`k = 1` 时由 `cancelFade` → `releaseFading()` 释放。修后 3.02s 才释放（11.2）。
4. **淡入淡出期间界面提前 3 秒跳到下一首**：接棒瞬间 `this.index = ni` + `setMeta(t)` + `notify(true)` 一起执行，
   而旧曲还在出声，界面已经变成下一首（8 秒演示轨上是 3/8 的时长）。改为「音频照常切、对外显示暂缓」：
   `swapToNext(keepOld)` 抓旧曲的 track/index/duration/position 存入 `uiHold*`，`snapshot()` 优先返回这一份，
   `fadeTick` 每 100ms 用 `fadeOld.currentTime` 推进旧曲进度，`cancelFade` 时清空并 `setMeta + pushSessionState + notify` 一次。
   UI 侧零改动——页面只消费 `snapshot()`，标题/封面/进度/歌词/队列高亮自动跟随。
5. **淡出期间外部操作不结算**：`pause/seek/next/prev` 都不调 `cancelFade`，而 3 秒窗口内拖动进度条或切歌时，
   新实例不会进 paused，`fadeOld` 就没人收尾，旧曲会混在音轨里继续淡出。已在 `pause()` / `seek()` / `fail()` 入口补
   `cancelFade(true)`；`next()` 在 hold 期间改为**只结算不 advance**（此时内核已接到"旧曲的下一首"，再 +1 会跳过一曲）。
   真机实测：暂停打断的 fade 只有 587ms（00:08:05.236→.823），拖进度打断为 448ms（00:09:17.336→.784），均 < 满 3 秒（**已核实**：hilog 时间戳）。
6. **桌面歌词标签状态不刷新**：`PlayerPage` 的 `deskOn` 只在自己被点过时才更新，重新进页面永远显示「桌面歌词」，
   而窗口其实开着（真机 23:24 撞到：标签写「桌面歌词」，系统窗口正在滚词）。改为 `aboutToAppear` 里
   `this.deskOn = this.core.deskLyricEnabled()`。
7. **CUE 三个虚拟轨共用整轨那份 LRC**（1.2.2 修）：整轨 `.lrc` 的行时间相对文件头，而虚拟轨 `position`
   相对片头（`seek(cueStart)` 后从 0 计），两者差一个 `cueStart`，于是三轨都从第 1 行唱。
   修法：`LrcParser.slice(text, cueStart, cueEnd)` 取窗口、逐行减 `cueStart`、窗口外的行丢弃，
   裁在 `LyricService.load` 解析之前，`doc.raw` 也一并裁过——AVSession 整份推送与逐行推送落同一坐标系。
   输出固定 `[mm:ss.cc]` 两位小数，因为这是系统桌面歌词唯一验证过的形态（11.3 的逐行高亮就是它跑通的）。
   窗口内一句词都没有时（如末轨）新增 `LyricDoc.cueEmpty`，页面说「这一轨没有歌词 / 整轨 LRC 未覆盖本段」，
   不再误报「磁盘上没有同名 .lrc」。真机三条断言全过：第 2 轨 00:04 = 「无缝与分轨」（原 9.5s 行）、
   第 3 轨 = 本轨无词、第 1 轨三行依次点亮（**已核实**：dumpLayout 文本 + 截屏）。

### 11.6 本轮踩到的坑（下轮别再踩）

1. **`hdc send` 会把目标目录化**：送 `cue-fix.wav` 进 Download，落盘成 `Download/cue-fix.wav/cue-fix.wav`。
   CUE 与音频就这样被拆成两级，反而逼出了「三级配对」——写扫描器时不要假设 CUE 与音频同层。
2. **`install -r` 会洗掉文件夹授权**：重装后日志 `preload failed {"code":13900001}`，索引还在但读不到文件。
   必须重新走「设置 → 音乐文件夹 → 添加文件夹 → 选 Download → 右上 ✓」，preferences 里的授权记录不随重装保留。
3. **桌面歌词悬浮窗会挡住点击**：「添加文件夹」后那个 ✓ 在 (1131,284)，正好被窗口压住，连点无效。
   要么先关窗口，要么 `swipe 600 380 600 1400 600` 把它拖走（会变成展开面板）。
4. **系统窗口会变「僵尸窗」**：`aa force-stop` 之后桌面歌词窗口仍停在屏幕上显示上一首的词/占位文案，
   此时 `uitest dumpLayout` 只返回该窗口的树，应用 UI 树拿不到，后续按文本点击全部失效。
   本轮最后靠重启设备清掉——**别用 force-stop 做干净环境，用真机重启或先关窗口**。
5. **重启设备后 hdc 会失联**：`hdc list targets` 只剩 `COM3/COM4 UART`，需在设备上解锁/确认调试授权才恢复。
   无人值守的验证流程不要把「重启设备」当常规手段。
6. **`uitest` 点击坐标要跟布局原子化**：错误横幅、标题换行都会让布局上下位移，先 dump 再点（两次命令）必漂。
7. **单时间戳严格递增**：LRC 里同时间戳多行会被解析成「正文+译文」，行索引随之错位，桌面歌词高亮落错行。
8. **`hdc file send` 的路径语义**：本地路径带 `/` 时会把**相对目录结构照搬到设备**（`.verify/samples/x.dsf` →
   `/data/local/tmp/.verify/samples/x.dsf`；`./x.dsf` 则建成同名**目录**）。要落到指定位置，必须 `cd` 进素材目录、只写裸文件名、
   目标以 `/` 结尾。绝对 Windows 路径会被拼到 cwd 后报 `no such file`。
9. **`Download` 只有 hdc 与 file_manager 能写**：`hdc shell dd/cp` 往里写是静默 0 字节（`0+0 records out`），
   但 `hdc file send` 可以（落盘属主 `file_manager`）。造素材要直接 `file send` 进 Download，不要走 tmp 中转。

### 11.7 仍未覆盖

- **交叉淡入淡出的听感**：日志已证明 3 秒双向包络与释放时机，但没有录音回采，无法断言"听不出缝、不爆音"。
- **ISO 未造素材**：这一轮只测了 APE / WV / DSF / DFF 四类；`.iso` 走同一条 `UNDECODED_SUFFIX` 分支，未单独点播。
  `.aiff/.aif` 已在第十二节作为自建解码链的素材验证（1.3.0 起可真播）。
- **锁屏歌词、播控中心歌词的实际呈现**：`lyric` 已给且系统侧日志回显确认收到，未逐屏截图。
- ~~**CUE 虚拟轨共用一份 LRC**~~：**已修（1.2.2）**。原状是整轨 `.lrc` 被三轨重复使用、都从第 1 行唱
  （截屏 W3：第三轨开头仍显示「低频探针」）。现在按 `cueStart` 裁窗平移，第 3 轨窗口内无词 → 提示本轨无词。
  仍存的限制：**不支持 `[offset:±N]` 标签**（整条解析链都没支持，带 offset 的音源会整体偏）；
  **纯文本（无时间轴）歌词不裁窗**——没有时间戳就无法判断哪些行属于本轨，只能整份静态展示；
  以及一轨若跨了 LRC 的"上一行持续显示"区间，开头那一小段没有高亮行（属语义取舍，不是 bug）。

## 十二、自建解码链（第八轮，v1.3.0）

Pro 2.0 的第一块。AFM 之前 AIFF/APE/DSD/WavPack 只能"扫得到、说得出为什么播不了"，
这一轮把"自己解 PCM"这条链从零打通，并接上第一个格式（AIFF/AIFC）。

### 12.1 工程与产物

| 项 | 结果 |
|---|---|
| 构建集成 | `entry/build-profile.json5` 加 `externalNativeOptions`（CMake → `cpp/CMakeLists.txt`，`abiFilters=arm64-v8a`） |
| 库名/体积 | `libs/arm64-v8a/libmiwen.so` **147,800 字节**（HAP 3,566,770 → 含 libc++_shared 1.26 MB） |
| NAPI 导出 | `open / read / seek / close / handles / version`；句柄是 number，native 指针不外泄 |
| 依赖 | 无第三方源码，AIFF 解析自写（PCM / `sowt` / `fl32` / `fl64`） |

### 12.2 真机验证（MLN-AL00 / 1.3.0）

| # | 断言 | 证据 |
|---|---|---|
| 1 | 自检自造 AIFF 正确 | 生成 **1,411,254 字节** = 54 + 352800×4；日志 `aiff written`，解析出 `AIFF 44100Hz 2ch 16bit 8000ms` |
| 2 | 能出声 | `RendererInClient [IncSoundData] channel: 2, L/R 非零`；07:00:28.566 起播 → 07:00:36.334 eof，实测 **7.77 s**（8 s 素材，末缓冲补静音提前收尾） |
| 3 | 曲库点播 | 30 s AIFF：`native playing ... dur=30000ms`，界面 `00:14 / -00:15` 正常推进 |
| 4 | 暂停 / 继续 | 点播放键 → `renderer paused`；再点 → `renderer started` |
| 5 | seek | 播放中把进度从 `00:04` 拖到 `00:24`，落点与界面一致 |
| 6 | 播完自动下一首 | `native eof -> advance`（07:05:02.822），随后 DSF/DFF/APE/WV 依次被识别层拦下（streak 1→4） |
| 7 | 直出在原生通道生效 | 打开直出后日志 `audioEffectMode=NONE`（此前该开关只作用于 AVPlayer） |
| 8 | 主链路未被改坏 | 从 AIFF 切到 WAV 分轨：`NativePlayer: renderer paused` → AVPlayer `initialized → prepared → playing`，无缝交接 |

### 12.3 本轮踩到的坑

1. **`AudioRenderer.write()` 自 API 11 起废弃**，编译期只给 deprecation 警告、运行期仍能写，但正确姿势是
   `on('writeData', cb)` 由系统按需索要数据。用旧 API 会绕过缓冲调度，长播偶发欠载。
2. **`napi_create_arraybuffer` 的长度必须按"实际帧数 × 声道 × 4"精确开**。第一版为了省事按容量开满，
   结果 JS 侧 `Float32Array` 尾部全是上一轮的残留数据 —— 听感上是每 100 ms 一点爆音，且只在多声道素材上暴露。
3. **`writeData` 回调里不能直接 `renderer.stop()`**：回调跑在音频线程，stop 要等该线程退出，互等后卡死。
   收尾一律 `setTimeout(0)` 抛回 UI 线程。
4. **采样率不做重采样**：素材 44100 就按 44100 建渲染器。第一版曾想"统一 48k"，那会让所有 44.1k 素材变调。
   现在不在支持范围就明确报错。
5. **NAPI 同步 read 够用**：AIFF 一次 100 ms 数据只是整型转 float（微秒级）。接 WavPack/APE 后若单次 >5 ms
   再挪 async work，不为还没发生的问题提前上复杂度。

### 12.4 仍未覆盖

- **来电/焦点抢占未实测**：`renderer.on('audioInterrupt')` 已注册（DUCK→25% 音量，PAUSE/STOP→暂停），
  但没有真实来电场景，只能说"接线正确"，不能说"行为已验证"。
- 多声道 >2、采样率 <8k 或 >192k：直接报错，未做降混/重采样。
- **CUE 分轨 + 原生格式**：暂不支持（时间片要裁 PCM，原生通道还没做窗口限制），点播给明确话术。
- ALAC / APE 两种格式未接（WavPack 已在第十三节接通），仍走 `UNDECODED_SUFFIX` 的拦截话术。

## 十三、自建解码链接 WavPack（第九轮，v1.3.1）

Pro 2.0「全格式真解码」第一步。AIFF 是裸 PCM，只需解析容器；WavPack 是真压缩格式，
熵解码不可能自写，因此**内嵌官方 libwavpack 5.8.1**，在已通的解码链上补一个格式。

### 13.1 工程与产物

| 项 | 结果 |
|---|---|
| 第三方源码 | `entry/src/main/cpp/wavpack/`，30 个文件 698,458 字节（24 个 `.c` + 4 个 `.h` + `wavpack.h` + `COPYING`） |
| 许可 | WavPack 5.8.1，**BSD-3**（保留原 `COPYING`，允许商业分发，无需开源本方代码） |
| 裁剪 | 去掉 `pack_dsd.c` / `unpack_dsd.c`（DSD 不在解码链范围）、去掉 `*.S` / `*.asm`（x86 与 armv7 手写汇编，arm64 走纯 C） |
| 编译宏 | `ENABLE_LEGACY`（解 WavPack 3.x 及更早旧文件）、`HAVE___BUILTIN_CLZ` |
| 库体积 | `libmiwen.so` 147,800 → **466,992 字节**（strip 后）；HAP 3,566,770 → **3,888,030** |
| 新增文件 | `fmt_wavpack.h/.cpp`（约 330 行），`decoder.cpp` 加 `wvpk` magic 分派 + `.wv` 白名单 |

### 13.2 验证素材与 PC 侧基准

素材由 ffmpeg 9.0.2 生成（三段拼接，左右声道不同频率，幅度逐段递增，便于按 RMS 反查值域）：

| 文件 | 规格 | 段结构 | PC 侧基准 RMS（每 2 秒） |
|---|---|---|---|
| `wv-16-44.wv` | 44100 / 2ch / 16bit / 30s | 0–10s：L440+R660 @0.3；10–20s：L880+R440 @0.6；20–30s：L1000+R500 @0.89 | **0.212 / 0.424 / 0.629** |
| `wv-24-96.wv` | 96000 / 2ch / 24bit / 10s | 全段 @0.5 | **0.354** |
| `wv-float.wv` | 44100 / 2ch / float32 / 8s | 全段 @0.4 | **0.283** |
| `wv-mono.wv` | 22050 / 1ch / 16bit / 6s | 全段 @0.5 | **0.354** |

> 基准值由 `ffmpeg -i x.wv -c:a pcm_s16le` 解出 WAV 后用 Python 逐 2 秒窗口算 RMS 得到。
> 设备侧日志 `level rms=` 是对解码输出抽样（步长 8）算的同一口径，两者能直接对照。

### 13.3 真机验证（MLN-AL00 / 1.3.1）

| # | 断言 | 证据 |
|---|---|---|
| 1 | 16bit/44.1 立体声正确识别 | `opened WavPack/无损 44100Hz 2ch 16bit 30000ms` |
| 2 | 时长与进度对齐墙钟 | 起播 07:42:00.826 → `native eof -> advance` 07:42:30.489，**墙钟 29.66 s**；位置 `@2043 → @28606 → eof`，无倍速 |
| 3 | **解码值域正确**（最关键） | 三段 rms **0.212 / 0.424 / 0.629**，与 PC 基准逐段一致；10 s、20 s 边界处出现 0.244 / 0.475 的混合窗口，符合窗口跨界 |
| 4 | 24bit / 96k | `96000Hz 2ch 24bit 10000ms`，rms **0.354** ✓（若按 16bit 缩放会差 256 倍） |
| 5 | 浮点 WavPack | `WavPack/float 44100Hz 2ch 32bit 8000ms`，rms **0.283** ✓（`MODE_FLOAT` 走位拷贝，不当整数转） |
| 6 | 单声道 | `22050Hz 1ch 16bit 6000ms`，rms **0.354** ✓ |
| 7 | seek 到 25 s | 点进度条后位置 `@25523`、rms 立即转 0.629（第 3 段）✓ |
| 8 | 暂停 / 继续 | 媒体键暂停 → `renderer paused`，随后 **7 秒内无任何 `level rms`**（位置冻结在 6130ms）；恢复后从 **6130 → 8173 → 10216** 接续，未回开头 |
| 9 | 播完自动下一首 | `native eof -> advance`，四个 wv 依次接播，无人工干预 |
| 10 | 主链路未被改坏 | 切到 `cue-test.wav`：AVPlayer `initialized → prepared → playing`，与原生通道互不影响 |

### 13.4 本轮踩到的坑（5 处，都是真崩/真错）

1. **`WavpackStreamReader64` 放在 `open()` 栈上 → 第一次 `read` 直接崩**。
   libwavpack 把 `reader` 指针存进 `WavpackContext`，每次解 block 都从那个指针回调；`open()` 一返回就是悬垂地址。
   真机表现：`opened WavPack/无损 ...` 之后 0.4 s 进程死，产生 cppcrash。改成成员变量后正常。
2. **`writtenFrames` 被累加两次**（本轮加电平统计时引入）。后果很有迷惑性：**声音完全正常**（墙钟 29.66 s），
   但界面位置翻倍显示 59 s，且日志里 rms 与位置错位 2 倍，一度让人怀疑解码器输出量翻倍。
   教训：位置类计数器只应有一处 `+=`。
3. **`WavpackSeekSample64` 返回 FALSE 之后上下文不能再读**。官方注释写明这是 fatal error：
   它在失败前已经 `free_streams(wpc)`，继续 `read` 会输出错位数据 —— 实测 rms 从 0.212 掉到 0.143/0.157，
   听感是电平骤降的噪声。正确做法是**关掉重建，再顺序解到目标帧**（`OpenContext` + `SkipFrames`）。
4. **重装后 fileShare 授权失效，但曲库仍显示旧缓存**。POSIX `fopen` 打不开 `/storage/Users/currentUser/Download/...`，
   而曲库列表照旧列出 17 首（读的是本地索引），极易误判成"解码器有 bug"。
   对照实验才定性：同一时刻**连 WAV 也播不了**，`PlayerCore` 报 `open real failed {"code":13900001}`。
   每次 `hdc install -r` 后都必须重走一遍"选择文件夹 → ✓"。
5. **`AVPlayer` 进 error 状态后持续回调 `error`**，而 `fail()` 没有去重，一首坏文件把失败处理打成
   **streak 482,840 次**（日志刷屏、界面卡住）。本轮加 `failHandled` 守卫：每轮起播只处理一次失败，
   并在 `fail()` 里 `releaseReal()` 把出错实例释放掉。

### 13.5 仍未覆盖

- **`.wvc` 校正文件未实测**：代码会在同目录自动找同名 `.wvc` 并 `OPEN_WVC` 挂上（大小写都试），
  但现有条件造不出 hybrid + `.wvc` 素材（ffmpeg 的 wavpack 编码器不产 `.wvc`），只能说接线正确。
- **hybrid 有损文件**未测（识别与时序逻辑同无损，差别只在是否挂 `.wvc`）。
- **DSD 编码的 `.wv`**：打开时明确报「这是 DSD 编码的 WavPack…暂不支持」，未做 DoP 输出。
- **长文件 seek**：无 block index 的文件走"重建 + 顺序解码"，上限 `44100×300`（约 5 分钟）；
  超过则回到开头。1 小时整轨拖到中段会退回开头而不是假报位置。
- 多声道 >2：`NativePlayer` 层拦下给话术，未做降混。

### 14.4 本轮踩到的坑（4 处）

1. **`EndianPortable.c` 漏判 aarch64**（Apple 源码的锅）：arm64 上 `TARGET_RT_LITTLE_ENDIAN`
   未定义 → 编译进大端分支。本文件只影响编码器路径，但同样漏判的还有 24bit 输出的
   LBYTE/MBYTE/HBYTE（matrix_dec.c 自带分支，小端正确）。已在 alac/EndianPortable.c 补判定。
2. **24bit 输出按大端拼字节**（我的锅）：Apple 解码器在小端主机输出**小端 3 字节**
   （LBYTE=0），第一版按 `b[0]<<16 | b[1]<<8 | b[2]` 拼成大端 → 正弦变噪声，
   真机 rms 恒 0.555、三段幅度差异完全消失。PC 端用 ffmpeg 解出参照 PCM 逐样本比对后定性。
3. **`read()` 把 float 个数当帧数**（我的锅，立体声下差 2 倍）：`pending_.size()` 是 float 数，
   memcpy 越界读了 vector 容量里的陈旧数据当音频。真机表现极其迷惑：**声音听起来是好的**
   （陈旧数据就是前一两秒的同段音频），但位置 2× 于实际产出、内容滞后约一半、
   30 秒的文件跑到 40 秒还没 eof。单声道文件侥幸不受影响（×1），只测 mono 就发现不了。
   定位靠临时加的 `stats(id)` 诊断通道：`out=495616`（解码产出）对 `writtenFrames=991190`
   精确 2 倍，才锁定是单位混用。
4. **cpp 侧 `OH_LOG_Print` 在本机不吐字**（原因未查清）：INFO 级、ERROR 级、换了 domain 都不出。
   临时改走 napi `stats(id)` → ArkTS 电平日志带出，事后保留为正式诊断通道
   （`level rms=... [pkt=22/323 out=90112 err=0 eof=0]`）。

1. **`.dsf/.dff` 没进扫描白名单**：从 `UNDECODED_SUFFIX` 移出时忘了加进 `AUDIO_SUFFIX`——文件根本扫不进曲库。教训：扫描名单和"暂不支持"名单是两个独立的闸口。
2. **DFF 采样率块匹配失败**：`memcmp(sub, "FSnn", 4)` 把通配写法当了字面 4 字节，真实块 ID 是 `"FS  "`（FS+两空格）。改为按前两字节 `"FS"` 比较；PROP 子块循环加边界保护防越界。症状：报「DFF 采样率字段异常」。

### 17.1 DST 编码器与素材（先有鸡后有蛋的问题）

公开渠道拿不到 DST 参考编码器（ISO PAS 官网已关停、HydrogenAudio 提到的 RefEncoder.zip 网盘链接失效、本机无 ffmpeg），于是按 DSTD 规范**自行推导**区间法算术编码器（`tools/dsd_material/make_dst.py`）：

- **解码器语义**（镜像 fmt_dst.cpp）：寄存器 c ∈ [0,A) 表示「码流窗口值 − 累积下界」，决策 e=1 ⟺ c < h（h = A − ap，ap = ⌊A/256⌋·p）。
- **编码器**：维护区间 [L, L+A)；e=1 → A←h，e=0 → L+=h、A←ap；renorm n = 11 − ⌊log2 A⌋，A、L 同步左移 n 位并累计。输出 N = L+A−1 的前 S = 12+Σn 位（MSB-first）。区间嵌套可归纳证明正确，450+10 帧 roundtrip bit-exact。
- **帧头 39 位**：1(DST),1,1,1(分段),1(same_map),0(map逐声道),0(half_prob), fsets{7位 len−1, 0(直接系数), 9位补码系数}, probs{6位 len−1, 0, 7位(值−1)}, 0(算术标志)，后接 12 位 c_init + renorm 位。
- **无预测帧**（coeff=0, probs=[128]）：p 恒 128，码率≈原始 100.1%；**FIR 帧**（coeff=8, probs=[128,96]）：predict=±8 查 status 字节 0，首决策 p=ProbDstXBit(8)=5，status 为 128 位滚动寄存器。
- 素材：`dsd-dst-1.dff`（450 帧、2,125,930 B）+ `dsd-dst-fir.dff`（10 帧、63,410 B），DFF-DST 容器（FRM8+PROP(FS/CHNL/CMPR='DST')+'DST'块{FRTE,DSTF×N}）。

### 17.2 SACD ISO 结构与位序（一手代码裁决）

所有偏移按 `scarletbook.h`（sacd-ripper 项目头文件，`refs/` 存档）逐字段累加核实，修正了 PROTOCOL.md 两条旧记录：`album_genre[4]`（4B×4）占 40..55 → `area_1_toc_1_start` 在 **@64**；区 TOC 里 `languages[10]`（4B×10）占 88..127 → `track_text_offset` 在 **@128**。

**位序结论**（曾一度误判，靠三份一手证据裁决后放弃"修复"）：小端机 `scarletbook.h` 的 LE 变体位域声明序 + sacd-ripper LE 分支显式移位 + 注释三方一致——扇区头字节 **bit0=dst_encoded、bit2..4=frame_info_count、bit5..7=packet_info_count（LSB 序）**；packet info 两字节按 **MSB 序**（bit7=frame_start，len=((b0&7)<<8)|b1）；DST frame info 第 4 字节 sector_count=(b3>>2)&31（LSB 序）。fmt_iso.cpp 原实现与此一致。

**扇区布局**：packet info 连续排在扇区头之后（整块 memcpy），载荷依次跟随——曾写错为"每个 packet info 放自己载荷前"导致 PC 验证失败。素材 `sacd-test.iso`（2950 扇区 5.8MB，450 帧×5 扇区，双声道不同信号防接反），`verify_iso()` 镜像全部解析路径 bit-exact 通过。

### 17.3 本轮抓出并修复的 bug

1. **fmt_iso.cpp 三处编译错误 + 一个交付 bug（重大）**：之前后台构建 exit 0 是**误报**——fmt_iso.cpp 从未编译通过。交叉编译设备端回归测试二进制（DevEco 自带 LLVM `--target=aarch64-linux-ohos`）抓出：(a) fmt_iso.h 缺 `#include "decoder.h"`；(b) SacdFeeder `dst_` 成员与 DstDecoder 成员重名 → 改 `dstEnc_`；(c) SacdSource 全类使用 `info_` 却从未声明；(d) PullFrame 交付用 `pendingDecoded_.data()` 类型错误且堆叠帧会被 `clear()` 丢弃 → 改 `front()` + `erase(begin())`。**教训：TaskOutput 拿到的 exit 0 不可信，必须看到 BUILD SUCCESSFUL 原文。**
2. **FLAC 回写块头 bug（本轮真机验证抓出）**：`WriteFlacTags` 替换 VORBIS_COMMENT 块时只压入 3 字节长度、**漏掉 1 字节块头（last 标志+type 4）** → 元数据区整体错位（第二块被当 14597 字节的"STREAMINFO"、last 标志落到内容中间、mutagen 读回 `tags=None`）。修复：替换分支补 `meta.push_back(h & 0x7F)`。修复后重验：块结构 STREAMINFO+VORBIS_COMMENT+PADDING 正确、mutagen 正常解析、STREAMINFO 音频指纹不变、音频区逐字节一致。**MP3 分支无此问题**（ID3v2.4→v2.3、TPE1 UTF-16 写入、音频帧 sha256 一致）。
3. **make_sacd_iso.py 两处**：s4 的第二个 packet info 误写到音频载荷后（应为与第一个连续排布在扇区头后）；验证公式两错（正弦均值应为 0 而非 (amp+1)/2；时长公式错）→ 改宽松均值平衡检查 + 正确时长换算。

### 17.4 真机断言与结果

- **DST**：`dsd-dst-1` 打开日志 `opened DSD64→PCM(软解)·DST 88200Hz 1ch 1bit 6000ms`，播放中 `rms=0.554`；`dsd-dst-fir` `133ms`（10 帧/75fps 精确）后自动接续下一首，rms=0.199。曲库行显示 DFF 标签正常。
- **ISO**：曲库「Download 本层」出现 `Miwen Track A`，艺人行 **"Miwen Audio · Miwen SACD Test"**（ISO 内 SACDText 读出）、格式 **"ISO · 88.2 kHz"**、时长 **00:06**（450 帧/75fps）。点播打开日志 `opened SACD-ISO(DSD)→PCM(软解) 88200Hz 2ch 1bit 6000ms`，AVSession 见 uri `iso:///storage/.../sacd-test.iso#mwi:0`，播放 `rms=0.199 [ sacd out=88200]`。
- **回写**：维护页选 Download 根目录（25 首）→ 填艺人 → 勾「同时回写到文件」→ 应用 → Toast **「索引 25 条；回写：成功 2，跳过 23，失败 0」**（23 个非 FLAC/MP3 正确跳过）。拉回文件独立解析见 17.3 第 2 条。
- **失败路径如实**：授权失效时同流程 Toast **「失败 2（打不开文件（可能是目录授权未生效））」**，不静默假成功。

### 17.5 环境与工具坑（复现验证必读）

1. **目录授权失效**：应用被杀/重启/重装后根目录授权失效（卡片"需重新授权"，native fopen 全部失败、AVPlayer 通道 libuv open 失败）。恢复路径：设置 → 音乐文件夹 → 管理 → 重新授权 → 系统选择器选 Download → 右上角 **✓** 确认 → 状态"可读"，**无需重扫**。
2. **SELinux 禁自编译 ELF**：shell 域执行 /data/local/tmp 下的自编译二进制 Permission denied（setenforce 不可用）→ 设备端独立测试二进制路线放弃，改走「应用本体 + hilog 断言」。
3. **hdc**：`file send/recv` 必须用设备绝对路径；shell 无法 cp 进用户 Download，但 `hdc file send` 可以（走 file_manager 通道）；Git Bash 下参数一律加 `MSYS2_ARG_CONV_EXCL="*"` 防路径转换。
4. **uitest**：列表滚动用 `dircFling 2`（swipe 的末参是速度不是时长，且起点落在底部迷你播放条会打开播放页）；**Toast 可在点击后立即 dumpLayout 抓到**（存活的 ~1.6s 窗口内）；`inputText` 是**追加**不是替换；键盘打开时按 Back 收键盘一般不重置表单。
5. **构建**：`DEVECO_SDK_HOME` 未设会报 00303217；daemon 内存不足报 00306056 → `--no-daemon` 稳。截图用 `hdc shell snapshot_display -f xxx.jpeg`（uitest screenCap 输出的 PNG 太大无法直接查看）。
