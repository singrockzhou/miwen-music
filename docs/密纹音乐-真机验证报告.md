## 二、真实音频播放（关键）

示例曲走的是计时器引擎，**不产生真实音频**，所以专门加了「播放自检」：内置 4 秒扫频 WAV，从 rawfile 落到沙箱后走真实 `openReal` 链路。

日志证据：

```
PlayerCore: state -> prepared
PlayerCore: state -> playing
CONTINUOUS_TASK: StartBackgroundRunningSubmit background task mode: 2, continuousTaskId: 462
PlayerCore: background audio task started
MC: controllerCallback {"appName":"密纹音乐","playState":2,"validCommands":["play","pause","stop","playNext","playPrevious","seek"]}
MC: collectSong ... playTimeTotal: 3.994 s
PlayerCore: state -> completed
```

- `prepared → playing → completed`：AVPlayer 状态机完整走通
- `playTimeTotal: 3.994 s`：系统统计的真实播放时长，与 4 秒测试音吻合，**不是 UI 假进度**
- 播放页显示 `WAV · 22.1 kHz`，总时长 `-00:03` 由 `durationUpdate` 回填（Track.duration 传的是 0）
- 播控中心（下拉控制中心）能拿到曲名、艺人、进度，`play`/`pause`/`stop`/`next`/`prev`/`seek` 指令齐全

| 4 | AVSession 刷 `img uri empty` | **试过一代方案后又回退了**。第一版：启动时把 rawfile 图落到沙箱，无封面曲目拿它的 `file://` 交给 AVSession。实测发现系统会拿 curl 去下载这个 uri，直接报 `URL using bad/illegal format` + `DoDownload failed` —— 4~5 条 E 日志，比原来更吵。改回"不传 mediaImage" | 回到起点，但结论明确：无 `READ_IMAGEVIDEO` 权限就拿不到媒体库 uri，播控中心封面在这版做不了；`img uri empty` 是一行无害提示 |

顺带修掉本轮暴露的一个真缺陷：

**进入播放页不主动拉快照**。`aboutToAppear` 只订阅 `onChange`，而"解码失败""暂停"这类静置状态不会再发通知，页面就会停在空快照上——错误横幅因此永远不出现。已在 `PlayerPage` / `MiniPlayer` / `Index` 三处补 `this.core.snapshot()` 首拉。

关于 2.5 秒的实际观感：错误文案在本机折成两行（`无法解码该文件（示例：APE/DSD 需要转成 FLAC 或 PCM）`），2.5s 够辨认"出错了 + 已跳过"，但读不完整段括注。想更从容有两条零风险路子：把文案缩成"无法解码该文件 · 已跳到下一首"（细节留在设置页说明），或依赖"连错 3 次停下"时横幅保持（目前已是这个行为）。

## 七、文件夹树与多根目录（第三轮，13:10–13:30）

本轮新增 Pro 1.1 的第二个功能。验证目标不是"能编译"，而是"三条最容易在真机崩掉的路径"：
老索引升级、重装后授权失效、多根并存与嵌套。

### 7.1 老索引升级（1.0 → 1.1）

1.0 建的索引没有 `root_path` / `folder` 两个字段。不处理的话，设置页显示 3 首、文件夹管理页显示 0 首
—— 同一份数据两处自相矛盾，用户第一反应是"这版把曲库搞坏了"。

启动时补一次归属，真机日志：

```
TrackStore:   adopted 3 orphan rows
EntryAbility: adopted 3/3 orphan tracks
```

管理页随即从「1 个目录 · 0 首」变成「1 个目录 · 3 首」，卡片显示「3 首 · 1 个文件夹」。
只在**恰好一个根**时执行：多根时无从判断哪首属于哪个目录，猜错比空着更糟。

### 7.2 重装后授权失效 → 重新授权救回

这是本轮最有价值的一条。`fileShare.persistPermission` 在重装后会失效：

```
LibraryService: probe /storage/Users/currentUser/Download failed code=13900001
```

界面如实显示「需重新授权」+ 左侧铜金竖线，管理面板里的文案也跟着变（「重新授权（当前打不开）」/「重装后需要」）。
重选同一个目录后：

```
LibraryService: picked file://docs/storage/Users/currentUser/Download
LibraryService: found 3 audio files under /storage/Users/currentUser/Download
```

`path` 不变、`uri` 变了，按 path 配回旧记录 —— **不重扫、不丢歌单、不联网**。
状态标签随即从「需重新授权」变「可读」。

### 7.3 本轮修掉的三个真缺陷

| 现象 | 根因 | 修法 |
|---|---|---|
| 重新授权后状态标签仍停在「需重新授权」，但日志里 probe 明明成功 | `ForEach` 的 key 只用 `root.path`，重新授权时 path 不变 → 判定"没变"→ 复用旧子组件，`@Prop` 收不到新值 | key 改 `path_alive_count`；根卡片同时从 `@Builder` 抽成 `@Component` |
| 同一首歌可能同时属于两个根 | 允许把某个已授权目录的**子目录**再加进来 | `RootService.add` 返回 `added/exists/nested/invalid` 四态，嵌套直接拒绝并说明 |
| 管理页显示「0 首」而设置页显示「3 首」 | 老索引 `root_path` 为空 | 启动时 `TrackStore.adoptOrphans` 补归属 |

顺带：`folderCount` 把"根下直接放的曲目"（`folder` 为空串）误算成一个文件夹，改成
`COUNT(DISTINCT CASE WHEN folder <> '' THEN folder END)`；`RootService.list()` 会清掉历史遗留的嵌套根。

### 7.5 仍未覆盖

- **多根目录下的真实交叉验证**：设备上只找到两个有音频的目录（`Download` 与其子目录 `com.freeplay.music.hm`），
  后者恰好是被父目录覆盖的嵌套场景，所以"两个互不相交的根各自扫描"只在逻辑层与 UI 层验证过，
  没有两个真实不同的音乐目录可测。
- **5000 首规模下的树性能**：`folderStats` 的 GROUP BY 在 3 首规模下无法体现耗时，
  按索引设计与分页策略预计无问题，但**没有实测数据**，不要在对外材料里写成"已验证"。
- **目录改名后的表现**：`folder` 存的是扫描时的相对路径，改目录名后旧记录会指向不存在的路径，
  直到重扫才更新。当前不会崩（播放时才报"文件已失效"），但也没有"检测到目录已改名"的提示。

2. **逐行歌词把元数据冲空**（已真机复核通过）：`pushLyricLine` 只推 `{assetId, singleLyricText}`，
   `setAVMetadata` 是整份覆盖而非字段合并，`title/artist/duration` 全部变空，`duration` 恰是系统算桌面歌词进度的基准。
   改为 `fullMeta(t)` 统一产完整元数据，逐行推送与清词都从这里取，再挂 `singleLyricText`。复核后高亮逐行跟随（11.3）。
3. **交叉淡入淡出其实是「硬切 + 淡入」**：`fadeTick` 一等到预加载就 `swapToNext()`，而 `swapToNext` 里立刻
   `quietRelease(oldP)`——旧曲在新曲起播的同一刻被销毁，日志显示 `crossfade start` 与 `seamless switch` 只差 **104ms**，
   与界面上写的「两曲交叠 3 秒」不符。改法：`swapToNext(keepOld = true)` 把旧实例挂到 `fadeOld`，`fadeTick` 里
   旧曲 1→0、新曲 0→1 同时走，`k = 1` 时由 `cancelFade` → `releaseFading()` 释放。修后 3.02s 才释放（11.2）。
4. **淡入淡出期间界面提前 3 秒跳到下一首**：接棒瞬间 `this.index = ni` + `setMeta(t)` + `notify(true)` 一起执行，
   而旧曲还在出声，界面已经变成下一首（8 秒演示轨上是 3/8 的时长）。改为「音频照常切、对外显示暂缓」：
   `swapToNext(keepOld)` 抓旧曲的 track/index/duration/position 存入 `uiHold*`，`snapshot()` 优先返回这一份，
   `fadeTick` 每 100ms 用 `fadeOld.currentTime` 推进旧曲进度，`cancelFade` 时清空并 `setMeta + pushSessionState + notify` 一次。
   UI 侧零改动——页面只消费 `snapshot()`，标题/封面/进度/歌词/队列高亮自动跟随。
5. **淡出期间外部操作不结算**：`pause/seek/next/prev` 都不调 `cancelFade`，而 3 秒窗口内拖动进度条或切歌时，
   新实例不会进 paused，`fadeOld` 就没人收尾，旧曲会混在音轨里继续淡出。已在 `pause()` / `seek()` / `fail()` 入口补
   `cancelFade(true)`；`next()` 在 hold 期间改为**只结算不 advance**（此时内核已接到"旧曲的下一首"，再 +1 会跳过一曲）。
   真机实测：暂停打断的 fade 只有 587ms（00:08:05.236→.823），拖进度打断为 448ms（00:09:17.336→.784），均 < 满 3 秒（**已核实**：hilog 时间戳）。
6. **桌面歌词标签状态不刷新**：`PlayerPage` 的 `deskOn` 只在自己被点过时才更新，重新进页面永远显示「桌面歌词」，
   而窗口其实开着（真机 23:24 撞到：标签写「桌面歌词」，系统窗口正在滚词）。改为 `aboutToAppear` 里
   `this.deskOn = this.core.deskLyricEnabled()`。
7. **CUE 三个虚拟轨共用整轨那份 LRC**（1.2.2 修）：整轨 `.lrc` 的行时间相对文件头，而虚拟轨 `position`
   相对片头（`seek(cueStart)` 后从 0 计），两者差一个 `cueStart`，于是三轨都从第 1 行唱。
   修法：`LrcParser.slice(text, cueStart, cueEnd)` 取窗口、逐行减 `cueStart`、窗口外的行丢弃，
   裁在 `LyricService.load` 解析之前，`doc.raw` 也一并裁过——AVSession 整份推送与逐行推送落同一坐标系。
   输出固定 `[mm:ss.cc]` 两位小数，因为这是系统桌面歌词唯一验证过的形态（11.3 的逐行高亮就是它跑通的）。
   窗口内一句词都没有时（如末轨）新增 `LyricDoc.cueEmpty`，页面说「这一轨没有歌词 / 整轨 LRC 未覆盖本段」，
   不再误报「磁盘上没有同名 .lrc」。真机三条断言全过：第 2 轨 00:04 = 「无缝与分轨」（原 9.5s 行）、
   第 3 轨 = 本轨无词、第 1 轨三行依次点亮（**已核实**：dumpLayout 文本 + 截屏）。

### 11.6 本轮踩到的坑（下轮别再踩）

1. **`hdc send` 会把目标目录化**：送 `cue-fix.wav` 进 Download，落盘成 `Download/cue-fix.wav/cue-fix.wav`。
   CUE 与音频就这样被拆成两级，反而逼出了「三级配对」——写扫描器时不要假设 CUE 与音频同层。
2. **`install -r` 会洗掉文件夹授权**：重装后日志 `preload failed {"code":13900001}`，索引还在但读不到文件。
   必须重新走「设置 → 音乐文件夹 → 添加文件夹 → 选 Download → 右上 ✓」，preferences 里的授权记录不随重装保留。
3. **桌面歌词悬浮窗会挡住点击**：「添加文件夹」后那个 ✓ 在 (1131,284)，正好被窗口压住，连点无效。
   要么先关窗口，要么 `swipe 600 380 600 1400 600` 把它拖走（会变成展开面板）。
4. **系统窗口会变「僵尸窗」**：`aa force-stop` 之后桌面歌词窗口仍停在屏幕上显示上一首的词/占位文案，
   此时 `uitest dumpLayout` 只返回该窗口的树，应用 UI 树拿不到，后续按文本点击全部失效。
   本轮最后靠重启设备清掉——**别用 force-stop 做干净环境，用真机重启或先关窗口**。
5. **重启设备后 hdc 会失联**：`hdc list targets` 只剩 `COM3/COM4 UART`，需在设备上解锁/确认调试授权才恢复。
   无人值守的验证流程不要把「重启设备」当常规手段。
6. **`uitest` 点击坐标要跟布局原子化**：错误横幅、标题换行都会让布局上下位移，先 dump 再点（两次命令）必漂。
7. **单时间戳严格递增**：LRC 里同时间戳多行会被解析成「正文+译文」，行索引随之错位，桌面歌词高亮落错行。
8. **`hdc file send` 的路径语义**：本地路径带 `/` 时会把**相对目录结构照搬到设备**（`.verify/samples/x.dsf` →
   `/data/local/tmp/.verify/samples/x.dsf`；`./x.dsf` 则建成同名**目录**）。要落到指定位置，必须 `cd` 进素材目录、只写裸文件名、
   目标以 `/` 结尾。绝对 Windows 路径会被拼到 cwd 后报 `no such file`。
9. **`Download` 只有 hdc 与 file_manager 能写**：`hdc shell dd/cp` 往里写是静默 0 字节（`0+0 records out`），
   但 `hdc file send` 可以（落盘属主 `file_manager`）。造素材要直接 `file send` 进 Download，不要走 tmp 中转。

### 11.7 仍未覆盖

- **交叉淡入淡出的听感**：日志已证明 3 秒双向包络与释放时机，但没有录音回采，无法断言"听不出缝、不爆音"。
- **Aiff / ISO 未造素材**：这一轮只测了 APE / WV / DSF / DFF 四类；`.aiff`、`.aif`、`.iso` 走同一条 `UNDECODED_SUFFIX` 分支，未单独点播。
- **锁屏歌词、播控中心歌词的实际呈现**：`lyric` 已给且系统侧日志回显确认收到，未逐屏截图。
- ~~**CUE 虚拟轨共用一份 LRC**~~：**已修（1.2.2）**。原状是整轨 `.lrc` 被三轨重复使用、都从第 1 行唱
  （截屏 W3：第三轨开头仍显示「低频探针」）。现在按 `cueStart` 裁窗平移，第 3 轨窗口内无词 → 提示本轨无词。
  仍存的限制：**不支持 `[offset:±N]` 标签**（整条解析链都没支持，带 offset 的音源会整体偏）；
  **纯文本（无时间轴）歌词不裁窗**——没有时间戳就无法判断哪些行属于本轨，只能整份静态展示；
  以及一轨若跨了 LRC 的"上一行持续显示"区间，开头那一小段没有高亮行（属语义取舍，不是 bug）。
