# 密纹音乐 · EQ / 参数化均衡器可行性说明

- 撰写日期：2026-11-25（基于 v1.7.0 代码现状）
- 结论用途：内部沟通与对外解释均可直接引用
- 证据标注规则：**[已核实]**（SDK 头文件/官方文档/真机日志/源码一手证据）、**[推断]**（工程判断）、**[待确认]**（缺信息）

---

## 一、结论先行

1. **2026-11-24 的旧结论「做不了 10 段 EQ」没有错，但它有三个前提**：①基于 AVPlayer 播放通道；②限定「不引入 Native 解码链」；③系统侧确实没有频段增益接口。这三个前提在今天**两个已经失效**：v1.3–v1.5 我们已经自建了解码链（当时评估为 XL 成本的那件事，已经做完了），系统侧则在 API 22 新增了 EQ 效果节点。旧结论是针对 v1.1 时代的正确答案，不是永久真理。
2. **「参数化均衡器」（自定义频点/Q 值/滤波器类型）在鸿蒙任何版本都没有系统实现**——这一点至今成立，且对任何竞品同样成立。市场上已有的 PEQ（如海贝音乐的参数均衡器）全部是**应用内自研 DSP**：自研解码引擎拿到 PCM 数据，在写入输出前自己做滤波。这不是平台恩赐的接口，是每家自己写的。
3. **在当前项目条件下，EQ / 参数化均衡器可行，成本 M**（约 3–5 人日，详见第八节）：我们的自建解码链在 `NativePlayer.fill()` 处就是标准的 DSP 插入点，且已实装比 EQ 复杂得多的 WSOLA 变速不变调。真正的工作不是"能不能做"，而是"排不排期、覆盖哪些格式、卖不卖钱"。

## 二、旧结论回顾：当时否决的是什么

2026-11-24 的《密纹音乐-Pro版技术验证》用两条独立证据链（SDK 静态 grep + 真机运行时探测）否决了 10 段 EQ，当时的证据**至今全部仍然成立**：

| 当时证据 | 出处 | 今天的状态 |
|---|---|---|
| 全 SDK 无 `AudioEffectManager` / 频段增益接口 | SDK `ets/api/` 全量 grep，0 条 | 仍成立（API 12 SDK 口径） |
| `AudioEffectMode` 仅 `EFFECT_NONE`/`EFFECT_DEFAULT` 两值 | `@ohos.multimedia.audio.d.ts:7852` | 仍成立 |
| `AudioLoopbackEqualizerPreset` 仅作用于耳返 | `audio.d.ts:8459` | 仍成立 |
| `getAudioEffectInfoArray(MUSIC)` 真机仅返回 2 种模式 | `.verify/pro-11-probe.jpeg`（真机探测） | 仍成立 |

**但当时隐藏了一个前提**：所有证据都围绕 AVPlayer 通道（当时的唯一播放通道）。文档同时写了"若坚持要 EQ，唯一路径是 AudioRenderer + Native 解码自建链路（XL），不建议在 Pro 1.x 阶段碰"——这句话精确预言了路径，只是成本判断基于"内核还不存在"的当时现状。**v1.3.0–v1.5.0，这个内核已经建成**（见第四节）。

## 三、客观平台限制（这部分是系统的锅，与项目无关）

以下限制逐条给证据，**对外解释时可直接引用**。

### 3.1 系统播放器通道无 DSP 插入点

`AVPlayer` 是黑盒：解码在系统内完成，应用拿不到 PCM，也没有效果插入接口。`AVPlayer.audioEffectMode` 只能设 NONE/DEFAULT 两态（`@ohos.multimedia.media.d.ts:2997`）。**任何**用 AVPlayer 播 MP3/AAC 的鸿蒙播放器，都不可能给这两个格式挂上应用侧 EQ。

### 3.2 API 12 SDK 无频段增益接口（旧结论的核心证据）

见第二节表格，四条证据至今成立。社区博客中流传的 `getAudioEffectManager().setEqualizerConfig()` 之类写法在官方 SDK 中**查无此符号**（本项目 2026-11-24 全量 grep 为 0 条）[已核实]，按一手证据规则不采信。

### 3.3 API 22 新增的 AudioSuite EQ 节点：存在，但有两个硬伤

华为官方文档（capi-native-audio-suite-base.h）[已核实]：

- `EFFECT_NODE_TYPE_EQUALIZER = 201`，**Since: 22**，10 个固定频段（31Hz–16kHz），增益 ±10dB；
- **硬伤一：固定输出格式契约 48000Hz / S16LE / 2ch**。对 Hi-Res 播放器意味着把 176.4kHz/32bit float 的 DSD 转出信号降格到 48k/16bit 才能进 EQ——音质损失与本产品"还原"的定位直接冲突；
- **硬伤二：只有固定频段图形 EQ，没有参数化**——无自由频点、无 Q 值、无 Low/High Shelf、无 PreAmp。"参数化均衡器"系统在任何版本都没提供。

### 3.4 系统级全局 EQ 是系统能力

影响所有输出流的全局均衡器属于系统/预置应用能力，第三方应用拿不到（3.2 的证据同样覆盖此点）。**若有竞品声称做了"全局 EQ"，要么是逐应用自行处理，要么使用了不可持续的非公开手段**[推断]——按我们自己的口径，这属于做不到且不试图绕过的事项。

## 四、当前项目条件：旧评估的地基已经变了

### 4.1 自建解码链已建成（XL 成本已沉没）

v1.3.0–v1.5.0 完成了当年评估中"等于重写播放内核"的全部工作，且每一步都真机验证过：

- 解码：FLAC、WAV、WavPack（libwavpack 5.8.1）、ALAC（Apple 官方解码器）、APE（MACLib 13.50）、DSD（dsf/dff）+ DST 解压、SACD ISO 直读（含 v1.7.0 多声道区）；
- 输出：自建 `AudioRenderer`，`NativePlayer.fill()` 把 float PCM 直写渲染器——**这个写入点就是教科书级的 DSP 插入位置**；
- DSP 能力已被证明：WSOLA 变速不变调（窗 2048/搜索 256/交叉淡化）实装并真机验证 RMS 与 PC 基准吻合。**biquad 级联的复杂度低于 WSOLA**——它是稳定的 IIR 滤波，没有搜索窗和拼接逻辑。

### 4.2 一张图看清插入点

```
文件 → [fmt_*.cpp 解码] → PCM(F32LE) → [★ EQ / ReplayGain 插入点 ★] → fill() → AudioRenderer → 系统
                                            ↑
                              biquad × N 级联 + PreAmp
                              EQ 关闭时逐样本旁路 = bit-perfect 直出
```

EQ 关闭 = 与现在的直出模式完全等价（逐样本旁路，零改动）；EQ 开启 = 应用内调音，**仍然旁路系统音效链**（renderer `audioEffectMode=NONE` 保持不变），与"还原"卖点不冲突、反而互补：关 EQ 是还原，开 EQ 是可保存、可分享的精确调音。

### 4.3 尚不具备的条件（如实列出）

| 缺口 | 性质 | 补齐成本 |
|---|---|---|
| biquad 滤波模块本身（含参数化：频点/Q/Shelf/PreAmp、按采样率重算系数、防 zipper noise 淡入） | 未写 | 小（约 300–400 行 C++，RBJ cookbook 标准公式） |
| EQ UI（10 段推子 + 参数化面板 + 曲线可视化 + 预设体系） | 未写 | 小–中 |
| **MP3 / AAC 不在覆盖范围**：这两类仍走 AVPlayer 回退通道（3.1 的客观限制） | 架构现状 | MP3 可内嵌 mpg123/minimp3（开源许可友好，与 libwavpack 同模式）补齐；AAC 无轻量可靠方案，[待确认] |
| ReplayGain（与 EQ 同插入点，规划中 P1 遗留项） | 未写 | 与 EQ 合并开发可摊薄 |

## 五、技术方案概要（证明"可行"不是空话）

- **滤波器组**：10 段 peaking biquad 级联（参数化模式下每段频点/Q/类型可调，20Hz–20kHz，±12dB），RBJ Audio EQ Cookbook 公式，双二阶直接 I 型；
- **采样率适配**：88.2k/176.4k/96k 等输出采样率下按实际 fs 重算系数（切曲目/切速率时重建），高频段折叠用标准做法[推断]；
- **防爆音**：增益切换用短窗系数插值（zipper noise 标准对策）；PreAmp 默认按最大正增益预扣 dB，防削波；
- **浮点链**：全链 F32LE，无定 点转换损失——这是自建链相对系统 EQ 节点（S16LE）的另一个硬优势；
- **验证方法**：沿用本项目已验证过的基准法——Python(scipy) 生成扫频/粉噪 + 逐段 RMS/频响基准，与真机输出比对，FLAC/WAV/ALAC/APE/DSD 各抽一类，另验"EQ off 逐字节等于直出基线"；
- **DSD 边界**：DSD→PCM 后同样在 PCM 域滤波，技术上无障碍；但海贝等竞品在 DSD/MQA 场景**主动关闭数字调音以保纯净度**（公开资料）[已核实]，我们建议同口径：DSD 默认 bypass、可开关，作为话术而非短板。

## 六、竞品对比：别人是怎么实现的

以公开资料最完整的海贝音乐（HiBy Music，鸿蒙版在架）为样本[已核实，来源见文末]：

| 竞品路径 | 实现基础 | 我方对应现状 |
|---|---|---|
| **PEQ 参数均衡器**（频点/Q/类型自由） | **自研「北极贝解码引擎」**拿到 PCM 后应用内 DSP，跨 Android/iOS/鸿蒙同一套 | 我们同样自研解码链（v1.3–1.5），路径一致、基础已备 |
| GEQ 10 段图形 EQ | 同上（应用内） | 同上；若偷懒走系统 AudioSuite 节点则受 48k/16bit 契约限制，不采 |
| MSEB 听感调音台 | PEQ 算法 + 动态处理封装成主观滑块 | 非本期范围，架构上可基于同一 DSP 插入点扩展 |
| **DSD/MQA 场景 PEQ/MSEB 不启用** | 主动 bypass 保原生解码纯净度 | 我们建议同口径（第五节） |
| USB DAC 独占输出 | 平台 USB Audio 能力 | 不在本说明范围（规划另议） |

**归纳**：同类鸿蒙播放器的 EQ 不是"用了我们没有的接口"，而是"走了我们当时没走的路"——自建解码链 + 自研 DSP。这条路我们 2026-11-24 已经评估过并因成本 XL 放弃，**随后 v1.3–v1.5 为了"真解码"这个更硬的卖点把同一条路走完了**。EQ 只是这条路上最后一段没铺的路面。

## 七、一句话区分两种"做不了"

| 说法 | 是否成立 | 准确表述 |
|---|---|---|
| "鸿蒙平台做不了 EQ" | **不成立**（就本项目而言） | 系统不做，应用自己做；解码链我们已自建 |
| "AVPlayer 通道挂不上 EQ" | **成立** | MP3/AAC 回退通道拿不到 PCM，除非补自解 |
| "系统没有参数化 EQ 接口" | **成立且永久** | 任何版本的系统都只给过（API 22 起）固定 10 频段图形 EQ，且 48k/16bit 降格 |
| "当时不值得做" | **当时成立** | XL 成本判断正确；如今内核已建，增量为 M，判断需要更新 |

## 八、开发成本与产品优先级建议

### 8.1 工作量拆解（自研 biquad 路径）

| 工作项 | 规模 | 说明 |
|---|---|---|
| C++ biquad 引擎（参数化 + 系数插值 + PreAmp + 按 fs 重建） | ~300–400 行 | 置于 fill() 前插入点；复杂度低于已完成的 WSOLA |
| 预设体系 | ~10 组 | 可直接参考官方 AudioSuite 内置 8 组增益表（BALLADS/CLASSICAL/POP/ROCK 等，官方文档已核实数值）[已核实] |
| ETS UI（10 段推子 + PEQ 面板 + 曲线可视化 + Pro 门禁） | 中 | 沿用既有 ActionPanel 试用门禁（原规划"EQ 试 3 次"直接复用） |
| 基准与真机验证 | 中 | 扫频/粉噪基准法（项目已有成熟流程）；验"EQ off = 直出基线逐字节一致" |
| 合计 | **M（约 3–5 人日）** | 建议版本：v1.8.0 候选 |
| （可选）内嵌 mpg123/minimp3 补 MP3 解码 | 中 | 使 MP3 也进 EQ 覆盖范围；与 libwavpack 接入同模式 |
| （可选）ReplayGain 扫描与应用 | 中 | 与 EQ 同插入点，合并开发摊薄成本 |

### 8.2 优先级建议[推断]

1. **支持做，且值得做**：EQ 是烧友付费意愿最直观的功能（原 Pro 规划第一梯队头牌即 10 段 EQ），竞品已实现形成事实压力，而我们的边际成本只剩 M——此时不做，等于让沉没的 XL 投资少收一块最容易变现的回报。
2. **定位话术**："直出"与"EQ"不冲突：EQ off = bit-perfect 还原（既有卖点不变），EQ on = 应用内高精度调音（F32LE 全链、不降格 48k/16bit——**这句正好是对走系统 EQ 节点的竞品的差异化打击**）。
3. **付费墙**：Pro 功能，试用 3 次门禁（原规划机制原样可用）。
4. **范围话术**：无损全格式 + DSD（默认 bypass，与竞品同口径）覆盖 EQ；MP3/AAC 暂不支持如实标注，MP3 视排期补自解。

## 九、结论（可直接引用的三个层次）

1. **客观平台限制**：鸿蒙系统不向第三方提供参数化 EQ；系统播放器（AVPlayer）无 DSP 插入点；系统自带的 EQ 效果节点（API 22+）固定 48k/16bit 输出且无参数化能力，对 Hi-Res 产品不可用。这些限制对所有鸿蒙播放器一视同仁。
2. **当前项目条件**：旧结论"做不了 EQ"的前提（未自建解码链）已被 v1.3–v1.7 的事实推翻——解码链、渲染写入点、浮点链、DSP 能力全部在位，缺的只是一个 biquad 模块和一套 UI，成本 M。
3. **行动建议**：将 EQ / 参数化均衡器列入 v1.8.0 候选，作为 Pro 付费功能实装（含真机基准验证）；对外口径从"系统没接口做不了"更新为"系统不做调音，我们自研解码链自己做，且不做 48k/16bit 的降格调音"。
